## The right pymoo encoding for your model

### Step A — Freeze the event list (the “things that must be scheduled”)

You need a fixed list of events `e = 0..E-1`. Each event contains:

* which course
* which group-set (or groups)
* required duration (`num_quanta`)
* allowed teachers
* allowed rooms
* allowed time windows

This is typically derived from `Course.json + Groups + instructor qualifications`.

✅ This makes the chromosome length fixed: **`n_var = E`**.

### Step B — Encode decisions as ints

For each event `e`, you can encode:

**Minimal (recommended):**

* `start_quanta[e]` as an int in `[0, T-1]`
* `room_id[e]` as int in `[0, R-1]`
* optionally `instructor_id[e]` as int in `[0, I-1]` if teacher is decision-variable

So chromosome is either:

* `X.shape = (pop, E)` if only start times (room/teacher fixed), or
* `X.shape = (pop, 2E)` (start + room), or
* `X.shape = (pop, 3E)` (start + room + teacher)

If you want a packed single int per event:

* `x[e] = start * R + room` (or `start*R*I + room*I + teacher`)

### Step C — Convert strings to integer indices once

Build maps once:

* `course_id -> idx`
* `room_id -> idx`
* `instructor_id -> idx`
* `group_id -> idx`

For `group_ids: list[str]`, you do **not** put the list into the genotype. You keep it in the **event metadata**.

For fast conflicts:

* represent each event’s groups as a **bitset** (46 groups fits in a 64-bit int)

  * `event_group_mask[e]` is `uint64`
  * two events overlap if `(mask1 & mask2) != 0`

This single design decision makes evaluation **very fast**.

```python
from pymoo.core.problem import Problem
import numpy as np

class SchedulingProblem(Problem):
    def __init__(self, events, rooms, instructors, time_quanta=42):
        self.events = events
        # Define bounds for each variable
        xl = np.zeros(2 * len(events))  # Lower bounds
        xu = np.zeros(2 * len(events))  # Upper bounds
        
        for i, event in enumerate(events):
            xl[2*i] = 0                    # start_quanta min
            xu[2*i] = time_quanta - 1      # start_quanta max  
            xl[2*i+1] = 0                  # room_idx min
            xu[2*i+1] = len(event.allowed_rooms) - 1  # room_idx max
            
        super().__init__(n_var=2*len(events), n_obj=2, xl=xl, xu=xu)
    
    def _evaluate(self, X, out, *args, **kwargs):
        # X.shape = (batch_size, 1098)
        F = np.zeros((X.shape[0], 2))  # Objectives: [hard_penalty, soft_penalty]
        
        for i, x in enumerate(X):
            # Decode numeric x -> SessionGene list
            schedule = self.decode_to_session_genes(x)
            # Use your existing evaluator
            hard, soft = evaluate(schedule, courses, instructors, groups, rooms)
            F[i, 0] = hard
            F[i, 1] = soft
            
        out["F"] = F
```

## 1. How does the fast evaluator handle partial time overlaps?

**It doesn't use bitmasks or interval trees. It expands every event into individual quanta and maps them into `(resource, quantum) → [events]` dicts.**

The quantum grid is **1 quantum = 60 minutes** (time_system.py: `QUANTUM_MINUTES = 60`), so "1.5 hours" is impossible — all durations are integer multiples of 1 hour. The partial-overlap problem you describe **cannot arise in this system**.

The core logic in fast_evaluator.py:

```python
for e in range(n_events):
    start_q = int(start[e])
    dur = int(duration[e])
    room_idx = int(room[e])
    instructor_idx = int(instructor[e])

    for q in range(start_q, start_q + dur):          # expand into occupied quanta
        room_occ[(room_idx, q)].append(e)             # per-quantum occupancy
        instructor_occ[(instructor_idx, q)].append(e)
```

This is a **quantum-expansion approach** — each event is "unrolled" into its individual quanta. A 2-hour event at slot 5 occupies quanta `{5, 6}`. A 3-hour event at slot 4 occupies `{4, 5, 6}`. Overlap is detected whenever `len(events_at_same_resource_quantum) > 1`. Group conflicts use the same pattern at fast_evaluator.py, expanding `(group_id, quantum)` tuples.

**This is correct and equivalent to the original `Timetable` evaluator** because the original system also works in integer quanta. There is no sub-quantum scheduling.

```python
start_indices = list(range(max_start + 1))
```

It has **no filtering by instructor availability or group availability**. The original system *does* model this — constraints.py has `InstructorTimeAvailability` as a **hard constraint** that checks part-time instructors:

```python
class InstructorTimeAvailability:
    kind: str = "hard"
    def evaluate(self, tt: Timetable) -> float:
        for gene in tt.genes:
            instructor = tt.instructor_for_gene(gene)
            if instructor.is_full_time:
                continue
            for q in range(gene.start_quanta, gene.start_quanta + gene.num_quanta):
                if q not in instructor.available_quanta:
                    violations += 1
```

The `Instructor` model has `is_full_time: bool` and `available_quanta: set[int]` fields (instructor.py). An instructor blocked on Tuesdays would have those quanta absent from `available_quanta`.

**What needs fixing:** build_events.py must intersect `allowed_starts` with the quanta where the assigned instructor is actually available, and the repair operator's `_reassign_event_to_avoid_conflicts` must filter candidate times by `instructor.available_quanta`. Similarly, `RoomTimeAvailability` exists in the original but is missing from the fast evaluator.

## 3. Show me the build_events sorting logic.

**There is no explicit sort in build_events.py. This is a latent bug.**

build_events.py gets event order from a random population individual:

```python
pop = generate_pure_random_population(1, ctx, parallel=False)
genes = pop[0]
```

Then iterates `for e, gene in enumerate(genes)` — so event order is whatever `generate_pure_random_population` produces.

The **good news**: `generate_pure_random_population` does guarantee deterministic order. The code comment at population.py states:

```
[!]  CRITICAL: GENE ORDERING GUARANTEE

This function creates genes in DETERMINISTIC ORDER for all individuals:
1. Iterates through context["groups"] (dict maintains insertion order in Python 3.7+)
2. For each group, iterates through enrolled_courses
3. Creates exactly ONE gene per (course, group) pair
```

The underlying `generate_course_group_pairs` iterates `groups` dict (insertion-ordered in Python 3.7+), and uses `sorted(sibling_ids)` for subgroup ordering (population.py).

**However**, build_events.py depends on this indirectly through a throwaway population individual. The **real risk** is: if `Groups.json` changes key order (e.g., entries are reordered), or if `DataStore` loading changes, the event-to-index mapping in the saved `.pkl` silently shifts, and any previously trained/saved chromosomes become scrambled.

**What should be done:** build_events.py should either:
1. Sort events by a stable key like `(course_id, course_type, sorted(group_ids))` after generation, or
2. Store the sort key in the `.pkl` and assert it matches at load time

Right now it's *technically* deterministic for a fixed `Groups.json`, but fragile across data changes.
